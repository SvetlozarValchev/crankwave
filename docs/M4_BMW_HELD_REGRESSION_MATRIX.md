# M4 BMW held operating-regression matrix

Status: frozen before implementation

This gate replaces the single BMW held listening request with one small, exact
RPM/throttle cross. It broadens the audible operating regression set without adding a
second simulation or presentation path.

## Frozen points and order

The request set contains exactly these four independent points in this order:

| Index | Stable point key | Scenario ID | RPM | Throttle |
|---:|---|---|---:|---:|
| 0 | `rpm1500-throttle0p85` | `bmw-m52b28-held-regression-rpm1500-throttle0p85` | 1500 | 0.85 |
| 1 | `rpm3000-throttle0p25` | `bmw-m52b28-held-regression-rpm3000-throttle0p25` | 3000 | 0.25 |
| 2 | `rpm3000-throttle0p85` | `bmw-m52b28-held-regression-rpm3000-throttle0p85` | 3000 | 0.85 |
| 3 | `rpm6500-throttle0p85` | `bmw-m52b28-held-regression-rpm6500-throttle0p85` | 6500 | 0.85 |

Point keys and scenario IDs are exact identity-bearing strings. They are not display
labels and must not be generated by locale-sensitive number formatting. A set with a
missing, extra, duplicated, reordered, or mutated point is invalid.

The three `0.85` points isolate the effect of RPM at fixed throttle across low, middle,
and high engine speed. The two `3000 rpm` points isolate the effect of throttle at
fixed RPM. Their shared `3000 rpm`, `0.85` intersection keeps the cross to four renders
and anchors it to the already accepted held listening condition.

`0.25` means 25 percent throttle command. It does **not** mean 25 percent load, 25
percent torque, or 25 percent BMEP. The held-speed test cell supplies whatever reaction
is required to hold the requested RPM. Every successful point must therefore report
the achieved 32-cycle net shaft torque, mean shaft power, and especially achieved net
BMEP; the implementation must not relabel throttle as load.

## Shared scenario contract

Every point owns a fresh engine, scenario, and provenance ledger. No mutable gas,
mechanics, sampler, presentation, or publication state crosses between points. Only
the RPM, throttle, stable point key, and scenario ID differ.

The following values are identical at all four points:

| Field | Frozen value |
|---|---:|
| Fixed preparation horizon / audible start | `6.44 s` |
| Trailing complete-cycle sample | `32` cycles |
| Audible duration | `15.0 s` |
| Total duration | `21.44 s` |
| Physics / capture rates | `10000 Hz` / `10000 Hz` |
| Source / acoustic / delivery rates | `192000 Hz` / `192000 Hz` / `192000 Hz` |
| Capture block / event capacities | `200` frames / `3800` records |
| Public seed | `0xC0FFEE` |
| Operating-state event ID | `held-regression-running` |

The exact integer boundaries are frame `64400` for the preparation endpoint and
audible start, and frame `214400` for completion at the physics/capture rates. The
audible output is exactly `2880000` frames; the complete 192 kHz timeline is exactly
`4116480` frames.

All four points reuse the current canonical BMW M52B28 operating-profile conditions:
the warm stock-accessory condition; ambient `101325 Pa`, `298.15 K`, and zero relative
humidity; profile-owned fuel; initial gas and crankcase temperature `298.15 K`; wall,
coolant, and oil temperature `363.15 K`; the operating core's exact crank-TDC reference
angle; and fired running state with ignition, fuel, and dyno enabled and starter plus
limiter disabled. The fixed-horizon sampler retains the latest 32 eligible complete
four-stroke cycles ending no later than frame `64400` and makes no stationarity or
convergence claim.

All four points also use the same current accepted BMW exhaust presentation built by
`make_bmw_p18_render_specification()`, including its content-pinned configured IR,
route conditioning, convolution, publication, audition mix, and mastering settings.
The matrix must not introduce point-specific gain, EQ, noise, IR, mastering, or
monitoring calibration.

## Sole request-set and CLI surface

The only public held-regression construction surface is:

```cpp
BmwM52b28HeldRegressionRequestSetResult
make_bmw_m52b28_held_regression_request_set();

contract::ValidationReport validate_bmw_m52b28_held_regression_request_set(
    const BmwM52b28HeldRegressionRequestSet &request_set);
```

`BmwM52b28HeldRegressionRequestSet` owns exactly four typed point requests in the
frozen order above. The factory has no calibration, duration, RPM, throttle, horizon,
or sample-count arguments. The exact validator rebuilds the canonical set and rejects
any structural, identity, engine, scenario, provenance, condition, or ordering change.
There is no public single-point factory; CLI selection is a view over this exact set,
not a caller-authored request.

The listening executable accepts these exact held-point selection tokens:

| CLI token | Selected point key |
|---|---|
| `held-rpm1500-throttle0p85` | `rpm1500-throttle0p85` |
| `held-rpm3000-throttle0p25` | `rpm3000-throttle0p25` |
| `held-rpm3000-throttle0p85` | `rpm3000-throttle0p85` |
| `held-rpm6500-throttle0p85` | `rpm6500-throttle0p85` |

This is a greenfield replacement, not a compatibility extension. Implementation must
delete `BmwM52b28HeldSpeedListeningRequest`, its result alias, the
`make_bmw_m52b28_held_speed_listening_request()` and
`validate_bmw_m52b28_held_speed_listening_request()` functions, their source/header
files and tests, the `bmw-m52b28-held-3000rpm-listening-v2` scenario identity, and the
generic CLI token `held`. None remains as an alias, forwarding wrapper, deprecated
entry point, parser fallback, or alternate scenario. Unknown tokens fail closed.

## Output claim

These clips are exhaust operating-regression outputs through the currently accepted
presentation. They are useful for hearing whether the engine remains coherent across
RPM and throttle, but they are not production-complete engine audio. There is no
independent physical intake source and no independent mechanical source in this
output. Presentation air noise is not an intake simulation. The matrix therefore
must not be described as a complete intake/exhaust/mechanical bake or as the final M5
fidelity result.

## Implementation and acceptance gates

Implementation is complete only when all of the following hold:

1. The sole request-set type, factory, exact validator, point keys, four scenarios,
   and CLI tokens above are implemented, and the old single-point API and token are
   absent from source, tests, build files, and installed headers.
2. Focused tests pin the exact set size and order, identities, binary64 RPM/throttle
   values, shared conditions, horizons, rates, seed, and presentation construction.
   Mutating any point or reordering the set must fail exact validation; the deleted
   `held` token and every unknown token must fail parsing.
3. Each point completes with one request-bound held-speed result containing exactly
   the latest 32 eligible cycles at the fixed horizon. Tests require finite complete
   torque accounting and reported achieved net BMEP; they do not invent an audio
   quality score.
4. The full test suite passes from a clean commit. From that commit, launch all four
   renders concurrently as separate processes. Each process must use its own new,
   uniquely named output directory so directory transactions, manifests, logs, and
   audio files cannot collide. A missing or failed point fails the whole matrix gate.
5. Record for every point its source commit, request identity, scenario ID, sampled
   cycle range, achieved net torque/BMEP/power, render time, output directory,
   audition-file SHA-256, and manifest SHA-256. Publish direct paths to all four
   `master.reference.audition.wav` files.
6. Stop and wait for the user to listen to all four clips. Do not mark the PLAN matrix
   item complete, freeze these renders as the regression baseline, or begin M5 until
   the user explicitly accepts the set or directs a correction.

Listening acceptance is the audio gate. Contract tests protect identities, mechanics,
sampling, and reproducibility, but do not claim to prove that a sound is good.
